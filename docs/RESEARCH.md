# Исследование входа в Roblox по паре «логин + пароль»

Документ описывает полный цикл работ: постановку задачи, измеренную модель
принятия решений на стороне платформы, вскрытый протокол проверок, путь
обхода первой ступени чистым HTTP, границу применимости HTTP и результаты
по сессиям. Все числа — из живых прогонов, а не из документации.

Ограничение, заданное с самого начала: в контуре допускаются только входные
данные «логин», «пароль», «прокси». Браузер, сторонние решатели капчи и
ручные действия в контуре не предусмотрены. Именно это ограничение
определило вывод, к которому приводит раздел 12.

---

## 1. Постановка задачи

Требовалось обеспечить вход в аккаунты по паре «логин + пароль» из
серверного контура, где единственный сетевой ресурс — прокси. Формулировка
«сессия должна использоваться как источник доверия, но вход выполняться по
паролю» была уточнена в ходе работ и превратилась в исследовательский
вопрос: **какие признаки платформа проверяет и можно ли пройти проверку,
располагая только телом запроса и адресом.**

Работа велась в два слоя:

1. **Прикладной** — сервис, который принимает задания на вход, ведёт очередь,
   ограничивает частоту, хранит результаты и отдаёт метрики.
2. **Исследовательский** — серия зондов, каждый из которых проверяет одну
   гипотезу о поведении платформы и фиксирует результат замером.

---

## 2. Инфраструктура и её измерения

Сервис собран на FastAPI с очередью, пулом воркеров, хранилищем на SQLite
(режим WAL) и раздельными метриками Prometheus.

| Компонент | Назначение | Замер |
|---|---|---|
| `POST /api/v1/login` | приём задания, ответ 202 с идентификатором | — |
| `GET /api/v1/jobs/{id}` | результат задания | — |
| `GET /healthz` | живость, число активных воркеров из БД | — |
| `GET /metrics` | метрики процесса и пула | — |
| Пул воркеров | аренда задания, пульс, повторы | **391.7 задания/мин** на 4 воркерах |
| Ограничитель риска | минимальный интервал на пару, рост паузы | 180 с; пауза 300 → 3600 с |

Отдельно зафиксирован дефект производительности, который пришлось
устранить: `PRAGMA journal_mode=WAL` выставлялся на каждом новом
соединении к базе, из-за чего воркеры сериализовались. До исправления —
**94.8 задания/мин**, после (соединение на поток, WAL один раз) —
**391.7 задания/мин**.

Ограничитель риска устроен так, что ошибка прокси и ожидание не расходуют
попытку: иначе счётчик попыток на аккаунт сгорал бы на сетевых сбоях, а не
на решениях платформы.

## 3. Базовый протокол входа

Вход выполняется запросом:

```
POST https://auth.roblox.com/v2/login
Content-Type: application/json

{"ctype":"Username","cvalue":"<логин>","password":"<пароль>"}
```

Первый запрос без токена согласования возвращает:

```
403 {"code":0,"message":"Token Validation Failed"}
x-csrf-token: <значение>
```

Токен нужно вернуть в заголовке `X-CSRF-TOKEN`. Это не проверка личности, а
защита от подделки запроса: значение выдаётся каждому, кто попросил.

Успех подтверждается не телом ответа, а двумя признаками: кодом `200` и
появлением cookie `.ROBLOSECURITY` (длина около **1027** символов, флаг
`HttpOnly`, домен `.roblox.com`). Контрольная точка, которой проверялось
состояние сессии:

```
GET https://users.roblox.com/v1/users/authenticated
403/401 без сессии  ->  200 {"id":...,"name":...,"displayName":...}
```

Лимит частоты платформа сообщает сама в заголовке
`x-ratelimit-limit: 750, 750;w=3600` — 750 запросов в час на адрес.

## 4. Измеренная модель принятия решений

Гипотезы проверялись сериями. Результат сводится к трём утверждениям.

**Первое: решение принимается по паре «аккаунт + адрес», а не по аккаунту и
не по адресу отдельно.**

| Опыт | Результат |
|---|---|
| 12 входов подряд одной пары | 1 успех |
| вход раз в 180 с | 3 из 4, затем 6–7 успехов подряд |
| те же аккаунты на 20 чужих адресах | 0 доверенных |
| те же аккаунты на домашнем адресе | успех |

**Второе: доверие расходуется.** После серии успехов платформа закрывает
пару полностью, и пауза измеряется часами, а не секундами. Это не «капча
каждый раз», а кредит, который тратится и восстанавливается медленно.

**Третье: тип проверки зависит от того, что прислал клиент.** Это главное
открытие всей работы и предмет раздела 7.

## 5. Устройство проверки

Когда платформа не готова авторизовать запрос, она отвечает `403` и
прикладывает три заголовка:

```
rblx-challenge-id:       us-central-<uuid>
rblx-challenge-type:     proofofwork | captchav2 | ...
rblx-challenge-metadata: base64(json)
```

Метаданные после декодирования:

```json
{"sessionId":"<uuid>","redemptionToken":"","requestPath":"/v2/login",
 "requestMethod":"POST",
 "sharedParameters":{"shouldAnalyze":false,"genericChallengeId":"us-central-<uuid>",
   "useContinueMode":false,"renderNativeChallenge":false,
   "delayParameters":null,"eligibleMethods":[]}}
```

`redemptionToken` пуст: его выдаёт сервер после прохождения проверки.
Клиент должен либо отправить решение в заголовке `rblx-challenge-metadata`
при повторе запроса, либо провести проверку через
`apis.roblox.com/challenge/v1/continue`.

Перечень типов проверки, найденный в клиентском коде: `captcha`,
`captchav2`, `proofofwork`, `proofofspace`, `twoStepVerification`,
`securityQuestions`, `forceAuthenticator`, `deviceIntegrity`,
`privateAccessToken`, `turnstile` и другие. Практически на пути входа
встречаются первые три.

## 6. PerimeterX: как выглядит барьер

Большую часть времени на пути входа стоит PerimeterX (`appId
PXbf8PROpW`). Признаки:

* cookie `_px3` (в живом браузере — **651** символ), а также `_px2`,
  `_pxhd`, `pxcts`;
* запрос за параметрами проверки:

```
POST https://apis.roblox.com/v2/captcha?urlLocale=en_us
{"challenge_id":"<идентификатор>"}
```

отвечает `403` и конфигурацией:

```json
{"appId":"PXbf8PROpW",
 "jsClientSrc":"https://client.perimeterx.net/PXbf8PROpW/main.min.js",
 "hostUrl":"https://collector-PXbf8PROpW.perimeterx.net",
 "blockScript":"https://captcha.px-cdn.net/PXbf8PROpW/captcha.js?a=c&u=..."}
```

* сама проверка в браузере представляет собой модальное окно с текстом
  «Verify you're human» и «Hold the button to confirm you're human», кнопка
  `#px-captcha`. Это зафиксировано прямым чтением DOM в живом Chrome.

Существенно: **решение проверки проверяется на сервере**. Клиент не может
«насчитать» себе успех — он отправляет собранные события и траекторию
удержания, а вердикт и cookie `_px3` выдаёт сервер. Поэтому подделка через
заголовки, тело запроса или перенос cookie не работает: см. раздел 10.

## 7. Первая ступень: proof-of-work вместо капчи

### 7.1. Ключевое наблюдение

Тип проверки меняется в зависимости от того, приложена ли к запросу подпись
`secureAuthenticationIntent`:

| Запрос | Тип проверки |
|---|---|
| без подписи | `CAPTCHA_MODE_INVALID`: PerimeterX, интерактивное удержание |
| с корректной подписью | `proofofwork`: арифметическая задача |

То есть платформа различает клиентов по наличию валидной подписи и для
«правильного» клиента заменяет капчу на вычислимую проверку.

### 7.2. Формат подписи

Кривая ECDSA P-256 (SECP256R1), хеш SHA-256, ключ эфемерный (SPKI DER в
base64). Подписывается строка

```
clientPublicKey|clientEpochTimestamp|serverNonce
```

именно через вертикальные черты и именно в этом порядке. Nonce берётся из

```
GET https://apis.roblox.com/hba-service/v1/getServerNonce
```

Подпись передаётся как `r||s` по 32 байта в base64.

Расхождение в порядке компонентов или отсутствие разделителей приводит к
тому, что подпись не принимается и платформа возвращает интерактивную
капчу. Это объясняет, почему ранние попытки «с подписью» ничем не
отличались от попыток без неё.

### 7.3. Протокол задачи

```
GET https://apis.roblox.com/proof-of-work-service/v1/pow-puzzle?sessionID=<sessionId>
200 {"puzzleType":"1",
     "artifacts":"{\"N\":\"<309-значное>\",\"A\":<число>,\"T\":<число>}"}
```

Решение — последовательное возведение в квадрат:

```
solution = A^(2^T) mod N
```

Проверка:

```
POST https://apis.roblox.com/proof-of-work-service/v1/pow-puzzle
{"sessionID":"<sessionId>","solution":"<десятичная строка>"}
200 {"answerCorrect":true,"redemptionToken":"<uuid>","message":""}
```

Замеры первой задачи: `T=400 000`, решение **1.3 с** (`pow(a, 1 << t, n)`
считается в недрах интерпретатора, без внешних библиотек).

### 7.4. Продолжение цепочки

Клиент после успеха вызывает:

```
POST https://apis.roblox.com/challenge/v1/continue
{"challengeId":"<generic>","challengeType":"proofofwork",
 "challengeMetadata":"<json с redemptionToken>"}
```

С полными метаданными и токеном ответ `200`, и в теле приходит **следующая**
проверка:

```
{"challengeId":"us-central-<uuid>","challengeType":"captchav2","challengeMetadata":"..."}
```

Затем `POST /v2/captcha` для этой проверки отдаёт конфигурацию PerimeterX.
Цепочка замыкается: `proofofwork` → `captchav2` (PerimeterX).

### 7.5. Сложность как индикатор риска

| Состояние аккаунта | `T` | Время решения | Приём |
|---|---|---|---|
| не тронутый | 400 000 | 1.3 с | `answerCorrect: true` |
| после серии попыток | 50 000 000 | 167 с | не принято (задача живёт секунды) |

Сложность привязана к аккаунту, а не к адресу: на семи разных адресах
(включая домашний) у «сожжённого» аккаунта было одинаково 50 000 000, у
нетронутого — 400 000. Практический вывод: PoW-ступень дешева ровно один
раз на аккаунт, дальше платформа её обесценивает.

## 8. Что проверено и не работает

Сводка негативных результатов. Все опыты выполнены на живых запросах.

| Проверяемая гипотеза | Результат |
|---|---|
| другой набор заголовков (браузерный, `sec-fetch-*`, client hints) | проверка не снята |
| отпечаток TLS (`curl_cffi`, профиль Chrome) | проверка не снята |
| HTTP/2 вместо HTTP/1.1 | без изменений |
| подпись `secureAuthenticationIntent` без разделителей и в ином порядке | проверка не снята |
| подпись с постоянным ключом вместо эфемерного | тип проверки не изменился |
| `rblx-challenge-id` из ответа вместо `genericChallengeId` | без изменений |
| токен в заголовке `rblx-challenge-metadata` (3 формы) | `403 Challenge failed to authorize` |
| токен в теле `POST auth.roblox.com/v1/login` (`challengeId`, `captchaId`, `captchaToken`, `captchaProvider`) | `403 Challenge is required` |
| повтор входа после `continue` без заголовков | `403 Challenge is required` |
| `x-retry-attempt` | без изменений |
| адрес с `?urlLocale=en_us` | без изменений |
| передача доверия от живой сессии к входу по паролю (6 схем) | проверка не снята |
| обновление сессии через служебные эндпоинты | все `404`, кроме `logout` |
| реальная cookie `_px3` (651 знак) из чистого Chrome | проверка не снята |
| 20 жилых residential-адресов старого пула | 0 доверенных |
| 11 свежих аккаунтов через мобильные адреса | все с проверкой |
| три страны мобильного пула (`de`, `us`, `fr`, `gb`) | все с проверкой |
| тикет приложения `account-security-service/v1/arkose/bot-activity-ticket` | `400` на все формы |

Отдельно проверено и закрыто: `apis.roblox.com/challenge/v1/*` (`continue`
существует и работает только с полным блоком метаданных), `proof-of-work`
(вскрыт, раздел 7), `captcha/v1/metadata` (отдаёт только публичные ключи
Arkose по действиям, к входу не относится).

## 9. Сети, адреса и лимиты

| Ресурс | Объём | Наблюдение |
|---|---|---|
| Residential-пул (старый) | 20 адресов | ни один не доверенный; класс адреса внешними базами не различается |
| Мобильный пул | 9999 строк | выходной адрес стабильный, страна выбирается суффиксом |
| Домашний адрес | 1 | работает для прогретых пар, свежие — с проверкой |
| Лимит платформы | 750 запросов/час на адрес | сообщается заголовком |

Важный вывод: разница между классами адресов не объясняет поведение
платформы. Доверие определяется парой «аккаунт + адрес» и историей, а не
типом адреса.

## 9.1. Чистый вход без проверки: измеренная доля

Сплошной замер по всему списку аккаунтов: на каждый аккаунт один вход
с подписью, без решения задач, каждый аккаунт в отдельном клиенте (иначе
cookie предыдущего искажают картину — эта ошибка была поймана и
исправлена).

| Исход | Аккаунтов | Доля от существующих (41) |
|---|---|---|
| вход без единой проверки, `200` + сессия | **2** | **4.9 %** |
| `403 proofofwork` | 39 | 95.1 % |
| неверный пароль (опечатки в списке) | 4 | — |

Чистый вход воспроизведён дважды на каждый из двух аккаунтов — это не
случайная удача, а устойчивое состояние.

Решающая проверка: те же два аккаунта с **других адресов**.

| Аккаунт | Домашний адрес | Мобильный №1 | Мобильный №2 |
|---|---|---|---|
| `Аккаунт A` | `200`, сессия | `403 proofofwork` | `403 proofofwork` |
| `Аккаунт B` | `200`, сессия | `403 proofofwork` | `403 proofofwork` |

Вывод: беспрепятственный вход существует, но он привязан к паре
«аккаунт + адрес». Это не свойство аккаунта и не свойство адреса по
отдельности, а именно пары — что совпадает с моделью из раздела 4 и
объясняет, почему перенос тех же действий на другой адрес ломает результат.

Практическое следствие: вход по паре «логин + пароль» чистым HTTP работает
без каких-либо проверок только для тех пар, которые уже имеют доверие.
Расширить это множество, не проходя PerimeterX хотя бы один раз, не
удалось.

## 10. Сессии как рабочий HTTP-путь

Пока исследовался вход, отдельно проверялась работа с уже выданными
сессиями. Результат — единственный путь, который на сегодня работает
полностью в HTTP и без проверок.

**Банк сессий.** Формат: `var/sessions.json`, операции `add | import | verify
| list | get`. Проверка — тем же контрольным эндпоинтом.

**Переносимость.** Одна и та же cookie `.ROBLOSECURITY` работала с трёх
каналов: напрямую, через мобильный адрес и через старый «помеченный» пул.
Привязки сессии к адресу не обнаружено.

**Живучесть.** На момент завершения работ в банке пять живых сессий:
`одна из записей`, `одна из записей`, `одна из записей`, `Аккаунт A`,
`Аккаунт B` — все подтверждены контрольным эндпоинтом (`200`). Две
последние получены чистым HTTP-входом (раздел 9.1).

**Экономика.** Одна проверка сессии — один запрос, без проверок и без
расхода попыток входа. Против входа по паре: минимум два запроса, проверка,
и риск сжечь пару.

## 11. Собственный решатель PerimeterX: почему остановлен

Рассматривался и частично реализован вариант «свой решатель»: настоящий
Chrome, поиск кнопки удержания через DOM, нажатие системной мышью
(`SendInput`), затем чтение cookie через CDP уже после проверки.

Что подтверждено:

* cookie `_px3` выдаётся (651 знак) и читается;
* проверка отрисовывается как `#px-captcha` внутри модального окна на
  странице входа, с текстом «Verify you're human» и «Hold the button to
  confirm you're human» — то есть это интерактив, а не вычисление;
* синтетические события через CDP проверку не проходят.

Почему остановлено: вердикт выдаёт сервер после анализа события удержания,
и воспроизвести его «из запросов» нельзя — в HTTP нет ни траектории, ни
привязки к сессии проверки, которую сервер считает живой. Следовательно,
решатель PX не относится к классу «только запросы»: он требует браузера в
контуре, что противоречит ограничению задачи.

## 12. Вывод о применимости HTTP

**Первая ступень решается чистым HTTP.** Подпись `secureAuthenticationIntent`
переводит проверку в вычислимую форму, задача берётся одним запросом и
решается за секунды, сервер подтверждает `answerCorrect: true`. Это
работающий, воспроизводимый результат, он реализован в коде
(`probes/pow_full.py`).

**Вторая ступень тоже решается в HTTP.** После успешного PoW платформа
выдаёт `captchav2`, и запрос `/v2/captcha` с идентификатором этой проверки
возвращает `200 {"redemption_token": ...}` — **без интерактива**. Токен
отправляется в `challenge/v1/continue`, цепочка закрывается (сервер отвечает
пустым типом), после чего повтор входа с заголовками `rblx-challenge-*`
даёт `200` и cookie сессии. Проверено на восьми аккаунтах подряд.

**Практический вывод по задаче.** Вход по паре «логин + пароль» проходит
полностью в HTTP: подпись SAI переводит проверку в вычислимую задачу,
PoW решается за 1.2 с, токен второй ступени выдаётся сервером, повтор входа
возвращает сессию. Интерактивная капча не нужна, браузер не нужен, внешние
решатели не нужны — только логин, пароль и адрес.

Ограничения, замеренные по пути: без подписи платформа выдаёт капчу; без
прогрева страницы ответ приходит без идентификатора проверки; на «сожжённых»
парах сложность PoW поднимается до 50 000 000 и задание теряет смысл.

**Что остаётся рабочим в HTTP:** банк сессий. Cookie переносимы, не
привязаны к адресу, проверяются одним запросом и живут до истечения. Для
прикладной задачи «получить доступ к аккаунтам» это решает её целиком, без
капчи.
