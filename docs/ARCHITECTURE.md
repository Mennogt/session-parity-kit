# Архитектура

Документ описывает устройство сервиса: модули, модель данных, жизненный
цикл задания, ограничитель риска и точки отказа. Английская версия:
[ARCHITECTURE.en.md](ARCHITECTURE.en.md).

## 1. Общая схема

```
клиент → api/ → store/ (SQLite, WAL)
                 ↑   ↓
              workq/ (sqlite | redis)
                 ↓
              worker/ (пул) → governor (пары) → flow/ → challenge/
                 ↓
              obs/ (Prometheus)
```

Разделение намеренное:

* `api/` не знает, как выполняется вход, — только принимает задание и отдаёт
  статус;
* `worker/` не знает, как устроен HTTP-обмен, — только арендует задание,
  вызывает `flow/` и пишет результат;
* `flow/` не знает про очередь и пул — только про протокол;
* `challenge/` подключается через интерфейс и может быть заменён.

## 2. Модули

### `api/`

| Файл | Ответственность |
|---|---|
| `main.py` | сборка приложения, подключение маршрутов, периодический сбор метрик |
| `routes.py` | обработчики: постановка задания, статус, список, живость, метрики |
| `schemas.py` | модели запроса и ответа (pydantic) |

Постановка задания возвращает результат сразу, если он успел появиться за
`wait_seconds`; иначе — `202` и идентификатор для опроса. Это убирает
необходимость в отдельном брокере для синхронных сценариев.

### `worker/`

| Файл | Ответственность |
|---|---|
| `main.py` | запуск пула, обработка сигналов, корректное завершение |
| `pool.py` | набор воркеров, общий ограничитель и метрики |
| `runner.py` | цикл: аренда → вызов `flow/` → запись результата → пауза |
| `governor.py` | пауза на пару «аккаунт + профиль», рост кулдауна |
| `metrics_server.py` | отдельный порт метрик |

### `flow/`

| Файл | Ответственность |
|---|---|
| `client.py` | полный обмен: согласование токена, вход, проверка сессии |
| `detect.py` | распознавание ответа: успех, проверка, ручной шаг, отказ |

Ключевое требование к `detect.py` — не путать «нужна проверка» с «ручной
шаг»: разные статусы ведут себя по-разному в очереди.

### `store/`

SQLite в режиме WAL. Соединение на поток (иначе воркеры сериализуются на
блокировке: замерено падение с 391.7 до 94.8 задания/мин).

| Таблица | Содержимое |
|---|---|
| `jobs` | задания: вход, статус, попытка, аренда, результат, ошибка |
| `profiles` | сетевые профили: адрес, состояние, счётчики |
| `workers` | воркеры: идентификатор, пульс |
| `pairs` | пары «аккаунт + профиль»: последний запуск, кулдаун, статистика |
| `meta` | служебные значения |

### `workq/`

| Файл | Ответственность |
|---|---|
| `base.py` | интерфейс очереди |
| `sqlite_q.py` | локальная очередь на той же базе |
| `redis_q.py` | очередь для нескольких хостов |
| `factory.py` | выбор по `SPK_QUEUE_BACKEND` |

Аренда с ограниченным сроком (`SPK_QUEUE_LEASE_SECONDS`): если воркер
погиб, задание возвращается в очередь и не теряется.

### `profiles/`

Модель профиля и пул. Профиль — сетевой адрес с состоянием: свободен,
занят, в кулдауне, помечен. Пул не допускает одновременного использования
одного адреса сверх `SPK_MAX_CONCURRENT_PER_HOST`.

### `procs/`

Уборка осиротевших процессов браузера: если браузерный узел падает, процесс
остаётся и держит память. Модуль находит процессы, чей родитель исчез, и
завершает их.

### `obs/`

Метрики Prometheus и публикация снимка состояния хранилища в датчики:
`jobs_by_status`, `jobs_in_state`.

## 3. Жизненный цикл задания

1. `POST /api/v1/login` — задание пишется в `jobs` со статусом `queued`.
2. Воркер арендует задание (`lease`), ставит `running`, обновляет пульс.
3. Ограничитель проверяет пару: если пауза не истекла — задание ждёт, не
   расходуя попытку.
4. `flow/` выполняет обмен. Возможные исходы:
   * `SUCCESS` — сессия получена и подтверждена;
   * `CHALLENGE_FAILED` — платформа требует проверку;
   * `MANUAL_REQUIRED` — нужен ручной шаг (двухфакторный и подобное);
   * `INVALID_CREDENTIALS` — неверная пара;
   * `PROXY_ERROR` — сетевой отказ, попытка не расходуется.
5. Результат пишется в `jobs`, пара обновляется в `pairs`.
6. При неудаче — повтор с ростом паузы, до `SPK_JOB_ATTEMPT_LIMIT`.

## 4. Ограничитель риска

Задача — не сжигать аккаунты. Правила:

| Правило | Значение по умолчанию |
|---|---|
| Минимальный интервал между попытками одной пары | 180 с |
| Базовая пауза после отказа | 300 с |
| Максимальная пауза | 3600 с |
| Сетевой отказ расходует попытку | нет |
| Ожидание расходует попытку | нет |

Пауза растёт экспоненциально и сбрасывается после успеха.

## 5. Масштабирование

| Узкое место | Решение |
|---|---|
| Блокировка SQLite | WAL один раз, соединение на поток |
| Один хост | `SPK_QUEUE_BACKEND=redis`, несколько воркеров на разных машинах |
| Много одновременных входов | `SPK_MAX_CONCURRENT_PER_HOST`, пул профилей |
| Браузерный узел | отдельный процесс, `procs/` для уборки |

## 6. Точки отказа

| Отказ | Признак | Поведение |
|---|---|---|
| Прокси недоступен | `PROXY_ERROR` | попытка не расходуется, профиль в кулдаун |
| Платформа изменила протокол | неожиданный код ответа | статус `CHALLENGE_FAILED`, запись в лог |
| Воркер погиб | истекла аренда | задание возвращается в очередь |
| База заблокирована | таймаут записи | повтор с паузой |

## 7. Наблюдаемость

* `/healthz` — число активных воркеров берётся из таблицы `workers` по
  пульсу (окно 30 с), а не из конфигурации.
* `/metrics` — длительность обмена, попытки по исходам, задания по
  статусам, трафик браузерного узла.
* Логи — структурные (`SPK_LOG_JSON=true`), с идентификатором задания.
