## 1. Согласование токена запроса (CSRF)

```
POST https://auth.roblox.com/v2/login
Content-Type: application/json
{"ctype":"Username","cvalue":"<идентификатор>","password":"<секрет>"}

→ 403
{"code":0,"message":"Token Validation Failed"}
x-csrf-token: eFWpI+05UE/g
```

Наблюдения:

- токен приходит в **заголовке ответа**, а не в теле;
- токен переиспользуется: один и тот же (`eFWpI+05UE/g`) отработал в нескольких
  запросах подряд, в том числе после смены тела;
- к токену привязан набор cookie (`__cf_bm` от Cloudflare). Без переноса cookie
  между запросами токен может инвалидироваться — хранить оба артефакта вместе;
- тело отказа имеет форму `{code, message}`, без массива `errors`. Код `0`
  означает «не ошибка логики, а требование протокола».

## 4. Узел проверки

### 4.1 Реально показывается не Arkose

Браузерная сессия с настоящей формой входа показала: проверку отдаёт
**PerimeterX (HUMAN Security)**, а не Arkose Labs FunCaptcha.

| Признак | Значение |
|---|---|
| Скрипт | `https://captcha.px-cdn.net/PXbf8PROpW/captcha.js` |
| Стили | `cdn.foundation.roblox.com/current/human-captcha/challenge.css` |
| Точка выдачи | `https://apis.roblox.com/v2/captcha` (403 → проверка) |
| Вид | «Verify you're human — Hold the button to confirm you're human» |
| Cookie | `_px3`, `_pxvid`, `pxcts` (PerimeterX) |
| Опознание в DOM | `[role=dialog]` с текстом `Hold the button`, `Reference ID <uuid>` |

флоу отношения не имеют. Метаданные `apis.roblox.com/captcha/v1/metadata`
по-прежнему отдают ключ Arkose, но на пути входа он не используется.

### 4.2 Чем отвечает HTTP-путь

```
POST /v2/login  (с токеном, верные креды, прокси)
→ 403
{"errors":[{"code":0,"message":"Challenge is required to authorize the request"}]}
```

Ни `metadata`, ни `captchaId` в ответе **нет**. То есть повторный обмен
собрать не из чего: прохождение возможно только в браузерном контексте.

Классификация исправлена: раньше такое сообщение уходило в
`MANUAL_REQUIRED` (по слову «challenge»), теперь — в `CHALLENGE_FAILED`
с точным текстом. Это дефект разбора, найденный на живых данных.

## 6. Лимиты

Заголовки на каждом ответе:

```
x-ratelimit-limit: 750, 750;w=3600
x-ratelimit-remaining: 747 → 745 → ...
x-ratelimit-reset: 1671
```

- окно — час, ёмкость 750 запросов на IP, считается **каждый** запрос
  (включая те, что заканчиваются 403);
- за серию замеров `remaining` убывал линейно, `429` не наблюдался;
- `Retry-After` **не подтверждён** — нужен выход за лимит, чтобы увидеть форму;
- практический вывод: при 750/час на IP одна и та же точка выхода даёт не
  более ~6 успешных потоков в минуту (2 запроса на поток). Требование
  «1000/мин» без большого пула прокси недостижимо арифметически, а не
  технически.

## 7. Инфраструктура перед платформой

`server: cloudflare`, cookie `__cf_bm`, `cf-ray`, `report-to`/`nel`.

Значит, TLS- и HTTP2-отпечаток клиента имеет значение. `httpx` даёт
отпечаток, отличный от Chrome; для паритета нужен клиент с имитацией
отпечатка (`curl_cffi`) — см. отклонение в README.

Собрано по живым опытам, все проверяемы командами из `probes/`.

| Аккаунт 0, тот же IP, **чистый HTTP** (`probes.m1 --no-proxy`) | **SUCCESS**, 2.7 с |
| Аккаунты 3/4/5, тот же домашний IP, чистый HTTP | проверка |

Вывод: решение принимается по **паре «аккаунт + адрес»** и по истории этой
пары. Свежий аккаунт без истории входов требует проверку с любого адреса;
после одного успешного входа с адреса пара становится доверенной и HTTP-путь
работает без браузера. Помеченный адрес ломает доверие даже прогретому
аккаунту.

## 9. Устройство проверки: полный протокол

Снято с браузера (`probes.challenge_protocol`) и проверено вручную

### 9.1 Обмен пары отдаёт заголовки, а не тело

```
POST /v2/login  -> 403
rblx-challenge-id:       ...
rblx-challenge-type:     ...
rblx-challenge-metadata: <base64 JSON>
```

Расшифровка `rblx-challenge-metadata`:

```json

  "challengeId": "us-central-<uuid>",
  "redemptionToken": "",
  "sharedParameters": {
    "shouldAnalyze": false,
    "genericChallengeId": "us-central-<uuid>",
    "useContinueMode": false,

    "eligibleMethods": []

Прежняя попытка слать `captchaId`/`captchaToken`/`captchaProvider` была
обращением к устаревшему контракту: платформа ждёт заголовки
`rblx-challenge-*` и заполненный `redemptionToken`.

### 9.2 Дальше — витрина PerimeterX

```

### 9.3 Подпись входа (SAI)

Браузер отправляет в теле входа ещё и подпись:

```json
"secureAuthenticationIntent": {
  "clientPublicKey": "<ECDSA P-256, SPKI base64>",
  "clientEpochTimestamp": 1793281405,
  "serverNonce": "<16 символов>",
  "saiSignature": "<ECDSA P-256 SHA-256, raw r||s, base64>"

```

Nonce выдаёт `GET apis.roblox.com/hba-service/v1/getServerNonce?urlLocale=en_us`.
Проверено пять вариантов подписываемого сообщения (`probes.sai_flow`) —
на решение о проверке это не влияет, ответ одинаков.

### 9.4 Токен искупления без интерактива не выдаётся

С настоящей cookie `_px3` (631 символ, снята чистым Chrome на том же IP):

```
POST /v2/captcha {"challenge_id": ...} -> 403, redemptionToken отсутствует
```

Проверка привязана не к наличию cookie, а к факту прохождения
интерактивного испытания внутри конкретного challenge. Без него
`redemptionToken` не появляется, а без него повторный обмен не принимается.

## 12. Сессия против входа: cookie решает задачу целиком

Проверка стоит только на входе по паролю (POST /v2/login). На использовании
готовой сессии её нет. Проверено на трёх настоящих .ROBLOSECURITY
(длины 1058, 1024, 1027).

| Канал | Результат |
|---|---|
| напрямую, домашний адрес | 200, личность подтверждена |
| мобильный прокси (DE) | 200, та же личность |
| старый помеченный пул | 200, та же личность |

То есть сессия **не привязана к адресу**: одна и та же cookie работает с
доверенного адреса, с мобильного и с помеченного. Это отличает её от входа
по паролю, где решает пара «аккаунт + адрес».
