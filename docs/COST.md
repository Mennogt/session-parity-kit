# COST — стоимость одного потока в трафике и времени

Замеры на реальных запросах через резидентные прокси, 29.10.2026.
Сырые данные: `fixtures/browser/traffic.json`, `var/proxy-ips.json`.

## Два пути к одной сессии

| | HTTP-путь | Браузерный путь |
|---|---|---|
| Запросов | 2 | 212 |
| Трафик | ~3 КБ | **5.05 МиБ** |
| Время | 0.60 с | 15.9 с до DOM + 10–15 с на проверку |
| Память | ~10 МБ | 200–400 МБ на контекст |
| Проходит проверку | только если её нет | 0 из 10 попыток |
| Цена на 1000/мин | 3 МБ/мин | **4.9 ГиБ/мин ≈ 296 ГиБ/час** |

Блокировка картинок, медиа и шрифтов даёт всего **17%** экономии: основной
вес — JavaScript (3.95 МиБ из 5.05). То есть «отключить картинки» проблему
не решает.

## Что это значит для требования 1000/мин

Браузерный путь: 1000 потоков × 30 с / 60 = **500 одновременных браузеров**.
Это 100–200 ГБ памяти и 296 ГиБ трафика в час. Не масштабируется ни по
железу, ни по деньгам — резидентные прокси продаются за гигабайт.

HTTP-путь: измерено **981 задание/мин на 16 воркерах** при задержке 600 мс.
Ограничение не в коде, а в лимите платформы: 750 запросов в час на IP.
1000/мин требует ~160 точек выхода (по 2 запроса на поток).

Вывод, который надо принять: **браузер — не путь к скорости.** Скорость даёт
HTTP-конвейер; браузер — редкое исключение для тех потоков, которым
платформа назначила проверку.

## Откуда берётся проверка

Из 6 профилей с разными IP проверку получили 4 (67%), два прошли сразу.
Значит доля проверок определяется репутацией адреса и прогревом профиля,
а не нашим кодом. Пока эта доля 67%, любой расчёт по браузерному пути
упирается в 296 ГиБ/час.

## Что сделано, чтобы трафик не утекал

1. `spk_browser_bytes_total` — счётчик реально переданных байт (CDP
   `encodedDataLength`), пишется на каждое браузерное прохождение.
2. `spk_browser_sessions_total{result}` — сколько контекстов открыто и чем
   закончилось.
3. `SPK_CHALLENGE_BROWSER_ENABLED` — выключатель браузерного пути целиком.
4. `SPK_BROWSER_BLOCK_ASSETS=true` — блокировка картинок/медиа/шрифтов
   (−17%, но бесплатно).
5. `SPK_PX_HOLD_SECONDS`, `SPK_PX_SESSION_WAIT` — ограничение времени
   удержания и ожидания, чтобы попытка не висела.

## Экономика, если считать не «логины», а «сессии»

Проверка привязана к аккаунту и не снимается ни IP, ни отпечатком
(`docs/FINDINGS.md`, п.4.4). Значит для каждого аккаунта нужен **один**
успешный вход, дальше живёт сессионная cookie.

| Модель | Трафик на 1000 аккаунтов | Когда |
|---|---|---|
| Проверка на каждый вход, каждый раз браузером | 5 ГиБ на 1000 входов, повторяется постоянно | так делать нельзя |
| Один браузерный прогрев на аккаунт, дальше HTTP | ~5 ГиБ однократно | если вход один раз на аккаунт |
| Аккаунт без гейта (с историей) | 3 МБ на 1000 входов | если гейт снят |

Разница между 3 КБ и 5 МиБ — 1700 раз. Поэтому вопрос «сколько IP» вторичен:
сначала надо понять, снимается ли гейт вообще.

## Порядок действий, если нужен реальный KPM
1. Гонять **только HTTP-путь**, браузер держать выключенным.
2. Поднимать долю потоков без проверки: прогревать профиль (cookie-банка
   переживает задания), не менять IP внутри одного аккаунта, не долбить
   один адрес.
3. Считать бюджет трафика заранее: `потоки_с_проверкой × 5 МиБ`.
4. Браузер включать точечно, под очередью с малым параллелизмом, и смотреть
   `spk_browser_bytes_total` — он растёт быстрее, чем кажется.
