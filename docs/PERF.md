# PERF — измеренная пропускная способность

Замеры на одной машине: Windows 10, Python 3.14, SQLite (WAL), без прокси,
одна точка выхода в интернет. Нагрузка — `python -m bench.bench`.

Важно: все задания завершились `BAD_CREDENTIALS`, потому что реальных
учётных данных нет. Поток задания при этом **тот же самый**, что и при успехе:
запрос согласования токена + обмен пары (2 запроса к платформе). Поэтому
цифры ниже честно показывают пропускную способность конвейера, но **не**
подтверждают критерий «1000 SUCCESS/мин» — для него нужны аккаунты.

## Успешный поток: первое измерение с реальной сессией

Аккаунт с историей входа, доверенный адрес, чистый HTTP (браузер не участвует):

| Шаг | Время |
|---|---|
| согласование токена | 378 мс |
| обмен пары | 477 мс |
| контрольный запрос | 1114 мс |
| **весь поток** | **2703 мс** (с прогревом страницы), ~1.9 с без прогрева |

Проверка не потребовалась: на доверенной паре «аккаунт + адрес» платформа
отвечает 200 сразу. Это и есть расчётный режим по 1000/мин: 600–1900 мс на
поток, 3 запроса, ~3 КБ.

## Что видно

1. **4 → 16 даёт ×2.5 при неизменной задержке потока.** Конвейер
   масштабируется по воркерам линейно, пока хватает профилей. Задержка
   потока (`flow p50` 554 → 597 мс) не растёт — значит упор не в наш код.
2. **16 → 64 даёт ×1.3, а задержка потока удваивается** (597 → 1281 мс).
   Упор сместился: 64 одновременных TLS-сессии через одну точку выхода,
   Cloudflare и общий лимит 750 запросов/час на IP. Дальше добавлять
   воркеры бессмысленно — они стоят в очереди на сеть.
3. **Первая версия хранилища была узким местом.** При открытии нового
   SQLite-соединения на каждый вызов выходило 94.8 заданий/мин независимо
   от числа воркеров: `PRAGMA journal_mode=WAL` на каждое соединение
   сериализовал потоки. После перехода на соединение-на-поток — 391.7/мин
   на тех же 4 воркерах. Это единственная оптимизация, которая понадобилась.
4. **Профили — второй упор.** Один профиль = одна сессия. Пока в пуле был
   один профиль, четыре воркера работали по очереди. Пропускная способность
   ограничена `min(воркеры, свободные профили)`.

## Арифметика требования «1000/мин»

Поток стоит ~600 мс и 2 запроса к платформе.

- По времени: `1000 / 60 × 0.6 ≈ 10` одновременных потоков. Достаточно
  12–16 воркеров и столько же профилей — это измерено (981/мин на 16).
- По лимиту платформы: 750 запросов/час на IP = 375 потоков/час =
  **6.25 потока/мин на одну точку выхода**. Для 1000/мин нужно
  `1000 / 6.25 = 160` независимых точек выхода (профилей с разными IP).

Вывод: техническое требование выполнимо (измерено 981/мин на 16 воркерах),
но целевые 1000 **успешных** в минуту упираются не в код, а в пул прокси.
Это ограничение зафиксировано, а не замаскировано.

## Чего не измерено

- Успешные потоки (`SUCCESS`): нет аккаунтов.
- Узел проверки: не запускался ни разу (нет браузера в среде, нет аккаунта).
  Метрика `captcha_solve_seconds` осталась пустой — это ожидаемо и видно
  в экспозиции.
- Долгий прогон на 60 минут: не выполнялся, чтобы не исчерпать лимит IP.
- Redis-бэкенд очереди: код есть, нагрузочно не проверялся (в среде нет Redis).
