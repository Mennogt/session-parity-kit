# 03. Компоненты

## 3.1 API-слой

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/api/v1/login` | принять задание; синхронный ответ или `202 + job_id` |
| GET | `/api/v1/jobs/{id}` | состояние и результат задания |
| GET | `/healthz` | живость координатора, очереди, пула |
| GET | `/metrics` | Prometheus-экспозиция |

Идемпотентность: повторный POST с тем же `job_id` возвращает существующее
задание, а не создаёт второе. Дедупликация по хэшу входа в пределах TTL.

Каждый ответ — валидируемая схема. Ошибки — единый конверт
`{status, step, detail, job_id}`.

## 3.2 Очередь и воркеры

- Redis как транспорт: список заданий + структура состояния.
- Пул воркеров — отдельные процессы, не потоки внутри API.
- Воркер забирает задание, берёт свободный профиль, исполняет поток,
  возвращает профиль в пул, пишет результат.
- Число воркеров задаётся конфигом/окружением. Один и тот же образ
  масштабируется от 1 до N без правок.
- Аренда задания с TTL: упавший воркер не блокирует задание навсегда,
  задание возвращается в очередь после истечения аренды.

## 3.3 Слой профилей

Профиль = прокси (HTTP или SOCKS5) + User-Agent + отпечаток окружения +
cookie-банк.

Правила:

- **Один профиль — один поток.** Параллельное использование запрещено.
- Профиль выдаётся под аренду, освобождается в `finally`.
- Состояние профиля сохраняется между заданиями: cookie-банк переживает
  рестарт воркера.
- Сетевые ошибки, таймауты и отказы помечают профиль как подозрительный;
  после N подряд профиль уходит в карантин и исключается из пула.

## 3.4 Слой прохождения проверки

Абстракция `ChallengeProvider` с одним методом:

```
solve(challenge_context, profile) -> challenge_token | ChallengeError
```

Реализация по умолчанию — браузерная, через автоматизированный контекст
(Playwright). Альтернативные реализации подключаются через конфиг, без
изменения вызывающего кода. Регистрация провайдеров — по имени в конфиге.

Обязательное условие: узел проверки проходит **интерактивно**, как в живом
браузере. Никаких предвычисленных токенов и подстановок.

## 3.5 Пул профилей: здоровье и ротация

- Периодический health-check вне активных заданий.
- Мёртвый профиль исключается немедленно, попадает в отчёт.
- Ротация при отказе, таймауте или явном лимите.
- Отказ профиля **не расходует попытку задания**. Лимит попыток — 3
  оплаченных ошибки, сетевые сбои в него не входят.

## 3.6 Ретраи

- Экспоненциальный бэкофф с джиттером.
- Ожидание по условию с таймаутом, не `sleep` как синхронизация.
- Классификация ошибки решает: ретраить, ротировать профиль или вернуть
  финальный статус.

## 3.7 Метрики

Обязательный минимум:

| Метрика | Тип | Смысл |
|---------|-----|-------|
| `jobs_total{status}` | counter | распределение статусов |
| `kpm_current` | gauge | подтверждённых потоков в минуту |
| `captcha_solve_seconds` | histogram | длительность узла проверки |
| `login_flow_seconds` | histogram | длительность полного потока |
| `proxy_fail_total` | counter | отказы профилей |
| `queue_depth` | gauge | длина очереди |

Плюс: `worker_busy`, `profile_pool_free`, `processes_orphaned_total`.

## 3.8 Наблюдаемость

- Каждый внешний вызов логируется с `job_id`, шагом, длительностью, кодом.
- Сырые ответы внешних сервисов сохраняются в `fixtures/` по требованию
  флага — для разбора инцидентов и обновления `ref/`.
- Логи структурные (JSON), без секретов.
